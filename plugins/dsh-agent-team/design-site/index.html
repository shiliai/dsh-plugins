dsh-agent-team v2 设计方案

从「自由文本委派」到「类型化任务契约」—— 把"值得派发"从模型判断下沉为架构保证 · 2026-09-23 草案 · DESIGN.v2.md

一句话:v1 用 jev 判断"这个自由文本任务简不简单";v2 用类型化任务契约(Task Contract)在接口层面锁定规格完整性与结果可验证性,再配上批量扇出、分层路由大脑、验收-重试-升级闭环。目标版本 0.2.0,team_delegate 行为完全不变。

01动机:v1 的五个结构性缺口

v1(0.1.0)已在生产运行,数据与实测暴露出五个结构性问题——它们不是参数问题,是自由文本接口本身的问题:

#缺口v1 实证v2 解法
❶规格完整性无保证:自由文本写得含糊,worker 就含糊执行worker prompt 只有一层前缀兜底契约 spec() 编译器:leader 填类型化表单
❷结果无验收:验收成本吃掉派发收益outputText() 原样返回结构 + 语义双层验收门,机器可判
❸每次派发都打 jev,重复任务反复付 1–2sjev 在 execute 第一步分层大脑:typed 任务路由 0 延迟
❹统计只积累不回流appendStats 只写不读滚动聚合 → 熔断先验,进路由决策
❺无批量扇出;能力事故重复踩UNSUPPORTED_REASONING_EFFORT 每次 spawn 时才发现分片并行 + 能力记忆(冷却期)

02设计公理:什么时候派发是划算的

来自路由讨论的结论——派发值得当且仅当以下四条同时成立。v2 的全部组件都是为了把这四条从 jev 的判断依据变成契约接口的结构属性:

📐 规格完整性

  • 一句话能写全任务
  • 接口:类型化 inputSchema + spec() 编译器
  • leader 填表,不写散文

✅ 结果可机器验收

  • 退出码 / schema / 条数对齐等客观校验
  • 接口:outputSchema + verify()
  • 错了能自动重试,再错升级

🧨 影响半径有界

  • read-only / workspace-write / external-effect 三级
  • external-effect 恒留 leader
  • 命令走白名单别名,不接受自由命令

📦 批量放大收益

  • 分片并行:N 项任务摊薄固定开销
  • 接口:shardable 声明 + 有界并发
  • 部分成功不丢弃

04核心抽象:TaskContract

interface TaskContract<I, O> {
  kind: string                    // 注册表键,如 'translate'
  inputSchema: JSONSchema         // team_task 入参校验(第一道结构门)
  outputSchema: JSONSchema        // worker 输出结构契约(spawn 时交给运行时)
  blastRadius: 'read-only' | 'workspace-write' | 'external-effect'

  spec(input: I): ContentBlock[]  // 规格编译器:类型化输入 → 完整 worker prompt

  verify?(input: I, output: O): Promise<VerifyReport>  // 语义验收(pass|fail|partial)
  shardable?: { itemsKey: keyof I; shardSize: number } // 批量声明

  defaultPolicy: { route: 'worker' | 'leader' | 'auto'; worker?: string; effort?: string }
  budget: { maxToolCalls?: number; timeoutMs?: number; maxTokens?: number }
  retries: number                 // 验收失败重试预算,默认 1
}

两个编译期保证,对应缺口 ❶❷:

  • 规格完整性是构造出来的:spec() 拿类型化输入渲染 prompt——路径、要求、输出格式全部来自 schema 校验过的字段,没有"忘了写输出格式"这种事;
  • 可验收性是构造出来的:结构层由 outputSchema 双重把关(运行时约束 + 引擎复验),语义层由 verify() 把关;两者都过才算 pass。

05内置契约(首批)

kind输入输出语义验收影响半径默认路由
translate{texts[], targetLang, style?}{translations[]}条数一致、非空、语言抽检read-onlyworker
extract{files[], fields}{records[]}schema 覆盖率,每文件至少一条或显式 missread-onlyworker
bulk-edit{edits[], paths[], dryRun}{changes[]}dryRun 先行;应用后 run-checks 通过才算 passworkspace-writeworker
run-checks{check(白名单别名)}{passed, summary, logTail}退出码即验收(确定性校验器)read-only(白名单内)worker
summarize{source, maxWords}{summary}词数上限、要点覆盖抽检read-onlyworker
format-convert{files[], toFormat}{outputs[]}转换器退出码 + 输出可解析workspace-writeworker
freeformv1 task 文本原文本无(语义无法机器验收)视任务auto → jev
关键设计:run-checks 的命令只接受配置白名单别名(如 checks: {typecheck: 'pnpm typecheck'}),不接受自由命令——把"外部效应"锁进窄接口,这是影响半径可控的前提。bulk-edit 的语义验收直接复用它:改完能过 typecheck/test 才算通过。

能力记忆(缺口 ❺ 的后半)

worker-health.json 持久化 spawn 错误分类(UNSUPPORTED_REASONING_EFFORT / model-not-found / provider down),标记 (worker, effort/契约) 不健康 + 冷却期(默认 30min)。选工顺序:契约覆盖 → 健康且有能力 → 近期失败率低 → costHint 低。v1 的事故从"每次 spawn 时发现"变成"一次发现,冷却期内不再踩"。

08验收门状态机

stateDiagram-v2
  [*] --> SpecCompiled: spec() 编译完整prompt
  SpecCompiled --> Spawned: 能力记忆选工 + preflight
  Spawned --> StructuralCheck: worker 完成(outputSchema 双重把关)
  StructuralCheck --> SemanticVerify: 结构 pass
  StructuralCheck --> RetryOrEscalate: 结构 fail
  SemanticVerify --> Passed: 语义 pass
  SemanticVerify --> RetryOrEscalate: 语义 fail
  RetryOrEscalate --> Spawned: "重试预算内:失败明细拼回 prompt"
  RetryOrEscalate --> Escalated: "预算耗尽"
  Passed --> [*]: 返回 leader(结果+验收报告)
  Escalated --> [*]: fallback-leader(诊断+worker原始输出)
  • 重试预算默认 1(契约可覆盖);重试 prompt = 原 spec + 验收失败明细 + "输出完整修正结果";
  • 部分成功不丢弃:扇出场景下通过的分片照常返回,失败分片单独列出,leader 可只补做失败部分;
  • 首片失败即中止:扇出快速失败(可配置关闭),避免 N 片全错放大浪费。

11安全边界(继承 v1 并收紧)

不变量机制
fail-open,永不阻塞任务每一层异常都路由回 leader;stats 写失败只 warn
worker 不可嵌套委派maxDepth = 0(同 v1),分片 worker 同样受约束
external-effect 恒留 leader半径门硬编码;maxDelegableBlastRadius 只能收紧不能放宽到 external
自由命令不可执行run-checks 只认白名单别名;别名未配置 = 契约不可用
预算硬上限每 worker:maxToolCalls / timeoutMs / maxTokens;超限即止并升级
统计不影响正确性聚合只作为路由先验;文件损坏按空处理,原子写

13里程碑与风险

阶段版本内容价值锚点
M10.2.0契约注册表 + schema 验收 + team_task + 验收门/升级 + stats v2补缺口 ❶❷(规格完整 + 可验收)
M20.3.0扇出 + 合并 + 部分成功批量经济学,缺口 ❺ 前半
M30.4.0分层大脑(缓存+熔断)+ 能力记忆 + 契约级选工缺口 ❸❹❺后半
M40.5.0team_stats + run-checks 白名单 + 文档(+ 可选声明式自定义契约)观测与安全收口
风险对策
契约过窄,leader 退回自己干freeform 恒在;观测 per-kind 使用率,按数据扩契约
worker 输出骗过 schema 但语义错语义 verify 抽检 + 熔断;bulk-edit 强制 run-checks 验收
扇出放大错误(N 片全错)分片独立验收 + 首片失败即中止余片(可配置)
判定缓存固化错误路由TTL + 输入骨架哈希(参数变即 miss);只存 route 不存结果
能力记忆文件损坏损坏视为空(降级为无记忆),原子写
本版明确不做:每条用户消息自动拦截路由(需 host 深度钩子,风险大收益存疑)· worker 结果再验证 cascade(验收门单层)· client UI(team_stats 足够)· 跨 session 共享工人池。
