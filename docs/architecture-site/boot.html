启动链路：从回车到 URL 打印

还原 dsh --profile web 敲下回车之后发生的一切。launcher 本体只有 8KB（apps/cli/src/bin.js）—— 它的全部工作是「选树、叠层、下传」，其余都是树内插件的事。

逐步细节

① launcher：只认识自己参数的游标

parseDshArgs（apps/cli/src/args.ts:112）只解析三组东西：--profile <name>、可重复的 --patch <path>（刻意非变参——变参会吞掉内层参数）、--dump-config / --dump-default-config。两个子命令：web（硬编码别名 = --profile web）和 plugin（转发 pnpm）。内层参数边界靠 helpOption(false) + allowUnknownOption() + passThroughOptions() 实现：launcher 不认识的第一个 token 起就是应用参数，连应用的 -h 都原样下传 —— 所以 dsh web --help 打印的是 web 应用自己的帮助。

陷阱应用参数的第一个 token 若恰好叫 web 或 plugin 会被 launcher 当成子命令截走（apps/cli/reference/README.md "App arguments"）。

② 环境快照：.env 有边界

loadLayeredEnv('dsh')（packages/boot/app-boot/src/index.ts:177-198）依次解析调用目录的 .env（project 层）与 $DSH_HOME/.env（user 层），但PATH、NODE_OPTIONS、GIT_*、代理/TLS、一切 DSH_*/XDG_* 前缀命中即抛错 —— 这些只能来自继承环境，防止 .env 劫持进程引导。每个值来自哪一层被冻成不可变快照，挂在树的 launchEnvironment 服务上。

③ 组合 profile：双锚解析与空根

  • 安装闭包符号链接：启动时对 dsh 安装包依赖闭包做 BFS，在 $DSH_HOME/profiles/node_modules/ 建幂等符号链接 —— 这是「内置插件永远来自安装」契约的运行时载体，同时让出树插件的 peer（同一个 cordis 实例！）全机器共享，服务注册表才不会劈叉。
  • bundle 双锚解析：dsh.profile.bundles 列表逐项先从 dsh 安装解析、再从 profile 目录解析。所以 @deepseek-ai/dsh-base 恒与运行中的 dsh 同源；我们的插件（profile 的 pnpm 依赖）则从 profile 解析。
  • 模板自动初始化：profile 目录缺 package.json 时，web/headless 命中模板（web: [dsh-base, dsh-web-app]）自动初始化；其余 profile 报错提示 dsh plugin add。
  • cordis.yml 恒为 []：每次启动强制重写（PROFILE_ROOT_CONFIG），防止 Loader 的写回机制把组合结果烤进文件。它的唯一意义是给 Loader 一个 include 根、把模块解析锚在 profile 目录。

④ 叠层与挂载

组合发生在内存里：composeEntries([bundlePatches…, profile.patches, homePatches, overlays]) 对空列表做一次 applyEntryPatches —— 与启动 include、与 --dump-config 用的是同一个函数。然后 boot()（packages/boot/app-boot/src/index.ts:757-802）建 root Context、提供 dshHomePath、装 Loader、注入两件 launcher 事实（cmdlineArgs 冻结 argv 快照、launchEnvironment），再以固定 id 挂载 root include。最后等树沉降并审计：没解析到模块的行、FAILED 的行、缺 inject 服务的行都会带名字抛错。

⑤-⑦ 行的激活：flag 如何压过配置

web 面的关键接力是「命令行服务」模式：web-startup 插件 inject: ['cmdlineArgs']，用自己的 commander 程序解析 --host/--port 后 ctx.provide('webStartup', values)；webserver 行声明 inject: [webStartup]，配置写 host: !!js ctx.webStartup.host ?? '127.0.0.1' —— flag 是优先级最高的临时配置，且 --help 时 provider 不发布服务，依赖行自然全部不激活，「打印 help 却绑了服务器」这类事故被服务依赖图在类型系统之外排除。--host 0.0.0.0 被 web-startup 直接拒绝（等于向全网暴露 RCE 面）。

⑧ live 层：改 patch 文件不用重启

启动完成后 launcher 兜底装一个 watch-only 的 HMR，精确 watch profile 与 home 两份 cordis.patch.yml；变更回调每次重新读取全部层并 structuredClone（include 按引用插入行，复用解析对象会让「删掉覆盖」失效），然后 entry.update() 事务性换树、失败回滚。这就是「编辑 cordis.patch.yml 热生效」的机制。

补丁层叠加顺序

#层说明
1bundle 层 × Ndsh.profile.bundles 列表顺序（dsh-base 恒第一）；我们的插件按安装顺序排在 web-app 之后
2profile 的 cordis.patch.yml项目/个人层：~/.local/dsh_home/profiles/web/cordis.patch.yml（实机样本：obsidian 的 vaultRoot、wecom 的白名单都在这里覆盖）
3home 的 cordis.patch.yml机器级偏好，压过 per-profile 层
4--patch overlay × Nargv 顺序；必须存在（缺失即报错）
5launcher 派生 overlayagent-presets 的 shipped-root、DSH_TELEMETRY_DISABLED 禁用补丁

后层胜，同层按数组序。patch 按 id 整行替换 config、不做深合并 —— 覆盖者必须复述想保留的每个键。

patch YAML 语法速查

patch 文件 = 顶层 YAML 数组，每项一个 loader patch entry（vendor/include/src/index.ts:145-156）：

字段语义
id定位目标行（含 group 子行，递归建索引）。非 insert 补丁必须带 id；未命中 → 警告并跳过
name校验目标行的插件模块名，不符则整条补丁跳过
insert追加行：无 id → 追加到顶层；有 id → 追加进该 group 行的 config 数组。新行立即进索引，同拍平列表里更晚的补丁可以打它
config整体替换目标行的 config，不深合并
disabled替换行的禁用标志 —— overlay 关行的正道（「禁用而非删除」）
inject / intercept / isolate替换对应 EntryOptions 字段
!!js expr任意位置可用；挂载期在该行注入完成后 with(ctx){eval} 求值，可用 ctx.<服务>、process.env、dshHomePath()
空文件陷阱空/纯注释的 patch 文件会解析成 null（不是列表）而抛错；想表达「空层」请写 []（packages/boot/app-boot/README.md）。

dsh plugin：pnpm 的诚意转播

dsh plugin --profile <name> <pnpm args…> 不发明包管理器：全部 pnpm 动词在 profile 目录内原样执行。dsh 只贡献三件事：

  1. 首次初始化：写 profile 三件套（package.json + 空的 cordis.patch.yml + pnpm-workspace.yaml，后者固定 nodeLinker: hoisted 保证扁平 node_modules）；
  2. 相对路径锚定：add . / link:.. 重写为用户调用目录的绝对路径（pnpm 的 cwd 是 profile 目录）；
  3. 安装对账：按安装结果（而非依赖 diff）更新 dsh.profile.bundles —— 新依赖解析出 dsh.bundle.patch 就追加为层，声明消失就移出。update 到「新版本才获得 dsh.bundle 声明」的包会自动激活。

git 安装失败时，报错会直接给出 allowBuilds 指引（pnpm ≥10 拒绝运行 git 依赖的 prepare 脚本）。这个契约的完整展开在集成机制一章。

--dump-config：不启动看树

dsh --profile web --dump-config 与 boot 走同一个组合函数，对每个层前缀做快照再 diff，输出带 # == 来源, patched by 层 注释的 YAML（可直接再加载），每行标注 origin 与 patchedBy；!!js 原样打印不求值；未命中任何行的补丁打到 stderr。变体 --dump-default-config 连 profile 用户层都不读 —— 层坏了也能看 bundle 层，这是坏层恢复的诊断入口。dump 拒绝携带应用参数：「dump 不跑应用的命令行 provider，印一棵与实际启动不同的树会误导」。

设计意图的通俗解释

  • 一切皆 patch，根为空 —— 把「产品由哪些插件构成」从代码问题变成数据问题：dump 可离线重现、用户层可覆盖任何行、bundle 之间靠 id 寻址而非相互 import。
  • 整行替换而非深合并 —— 防幽灵默认值：若合并，bundle 后来新增的键会悄悄改变用户覆盖行的行为；整行替换迫使覆盖者显式复述，每行最终值永远只在唯一一层可见。
  • launcher 不认识应用 —— 新增一个带命令行的 app 不需要改 launcher 一行代码；每个 app 拥有自己的 --help。
  • 双锚解析 —— 内置 bundle 与运行的 dsh 同源（不能运行 0.1.2 却加载用户 profile 里的旧版 base）；出树插件归 profile 的 pnpm 管。
  • dump 与 boot 同函数 —— 从机制上杜绝「dump 显示的树与实际启动不一致」这类最消耗信任的偏差。
