宿主服务面：插件能 inject 到什么

出树插件与宿主的全部交互都通过 ctx 上的服务与事件。本页逐个过核心服务的契约与「我们的插件怎么用它」。服务的权威文档由源码生成在 docs/subsystems/*.md —— 官方明确要求以生成区域 + TS 接口为准，不维护第二份静态清单。

tools — 工具注册表与执行管线

ToolRuntime（packages/core/tools/src/index.ts:787，static inject: ['systemPrompt']）。注册 API 与作用域：

  • ctx.tools.register(definition) —— 全局注册；若经 agent.ctx 注册则落在该 agent 作用域（scoped 遮蔽全局）；
  • scoped 面还有 restrict(filter)（allow/deny 过滤全局工具）、guard(g)（单调守卫：返回字符串即拒绝，不可被翻回允许）、presentAs(mode)。

defineTool（packages/core/tools/src/schema.ts:545）的核心设计是「规范值 + 渲染」分离：execute 返回 output.schema 声明的规范 JSON 值，output.render(args, value) 再投影成模型可见内容 —— 同一份结果可以既给模型又给 UI。可选的 presentCall/presentResult 声明 UI 卡片渲染意图（纯函数、重放安全）。执行管线事件（全部 scope 过滤）：tools/pre-execute（waterfall，allow/deny/ask）→ tools/execute（around，可换 signal）→ tools/post-execute（accept/replace/block）→ tools/result（emit，冻结观察）。

// dsh-wecom 的出站工具 plugins/dsh-wecom/src/tools.ts:12-55
ctx.tools.register(defineTool({
  name: 'wecom_send_message',
  description: '向企业微信单聊/群聊推送 Markdown 消息',
  parameters: { chatId: {…, required: true}, content: {…, required: true} },
  isConcurrencySafe: () => false,   // 串行执行
  async execute(args) {
    if (!isAllowed(args.chatId, outboundAllowChats)) throw … // 默认拒绝
    return { ok: true, message: … }   // 规范值
  },
  output: { schema: {…}, render: (_a, v) => [{ type: 'text', text: … }] },
}))

agents — Agent 注册表与工厂

AgentRegistry（packages/core/agent/src/index.ts:256）。真正的构造由 dsh-agent-loop 通过 setFactory 注入。两个入口：

  • ctx.agents.create(options): Promise<AgentHandle> —— sessionId、meta（cwd/preset/origin…）、agentOptions（provider/model）、seed（fork 前缀）、setup(agentCtx)；
  • ctx.agents.resume({resumeSessionId, …}) —— 恢复持久化会话，要求 sessionPersistence 存在。

setup 的事务语义（index.ts:114-132）是理解插件如何「定制一个 agent」的关键：factory 先铸 agentCtx → await setup → 执行 setup 返回的同步 commit → 最后才发布 session 与 agent。setup 里注册的 scoped 工具、prompt section、preset 挂载都先于首次 prompt 组装存在；setup 抛错则整体回滚。AgentHandle = { agent, dispose() } —— 只有持有者能拆掉这个 agent。

// dsh-wecom ensureAgent 的 setup（plugins/dsh-wecom/src/index.ts:614-741 精简）
const selection = ctx.get('agentDefaultModel').currentSelection()
const preset = await resolvePreset(ctx.get('agentPresets'), …)
const created = await agents.create({
  sessionId, meta: { cwd, agentPreset: preset.id }, agentOptions: { provider, model },
  setup: async (agentCtx) => {
    installModelSelection(agentCtx, { current: selection })  // 模型选择快照进 agent 作用域
    await ctx.get('agentPresets').mount(agentCtx, preset.id) // 挂载 preset 组合
  },
})

agentDefaultModel / agentPresets

AgentDefaultModelConfig（packages/core/agent-default-model/src/index.ts:64）：currentSelection(): { provider, model, reasoningEffort? } 与 saveSelection()；有 settings 服务时挂 agent-default-model 命名空间让用户层实时覆盖。installModelSelection(agentCtx, ref)（从 @deepseek-ai/dsh-agent 导出）在 agent 作用域装两个 waterfall 监听（system-prompt/assemble 快照模型、agent/request 应用到请求），实现「并发切模型在下一步生效而不撕裂组装面」。

AgentPresets（packages/preset/agent-presets/src/index.ts:82）：每个 preset 是一份 cordis.yml 组合，按 preset 挂载为常驻 scope（standing mount），文件变更启动下一代 mount、已加入的 session 留在原代。核心 API：mount(agentCtx, id?)（在 agent factory 的 setup 里调，失败回滚整个创建）、composeFrom()（子 agent 继承父组合）、recompose()、list()/resolve()/copy()/remove()。dsh-wecom 的 /agent 命令就是它的消费面。

sessions — 事件溯源会话

SessionStore（packages/core/session/src/index.ts:792）。核心事实（文件头注释）：append-only 事件日志 + 内存 store + 派生的 LLM 消息史；持久化是插件的事。API 面：create/prepare/enter/announce、flush(session)（唯一 flush 入口，session/flush parallel 事件让持久化插件检查点）、fork()（从活 source 的完整回合前缀派生子会话）、get/list。

事件类型（SessionEventMap）是可 merge 扩展的 —— 插件可以声明自己的会话事件类型，只要 lossless-JSON 可序列化。事件携带 { type, seq, time, data }。这就是 dsh 那条架构铁律的落点：model-visible means logged —— 凡到达模型请求的输入必须能从日志重建（有运行时不变量断言），所以新的模型可见输入 = 扩展 SessionEventMap。

sessionPersistence — 缝的样板

抽象类 SessionPersistence（packages/session/session-persistence/src/index.ts:84）只定义契约：locate/create/append/load/inspect/readFrom/list/listSnapshots；实现有两个 Provider —— JSONL（默认，zstd 压缩帧）与 SQLite。web profile 装 JSONL 后端；headless profile 没有。消费方用可选依赖模式：dsh-wecom ctx.get('sessionPersistence') 判空降级（plugins/dsh-wecom/src/index.ts:532），定义结构子集接口 SessionPersistenceLike 而不是 import 实现。这是 Service Definition / Provider / Consumer 三角色分离的教科书案例。

webServer — 裸 HTTP 路由表

WebServer（packages/host/webserver/src/index.ts:59）：node:http 裸服务器 + 路由表，不懂任何 harness 概念、不服务任何文件。API 只有四个：

API语义
register({kind, path, handler})exact 或 prefix 路由；重复 (kind,path) 抛错；匹配「exact 优先、最长前缀胜」
registerUpgrade(route)exact path 的 HTTP upgrade（WebSocket）
registerFallback(handler)唯一席位：未被认领的请求（SPA dist 服务器占用）；第二个注册者抛错
tapIndex(transform)index.html 变换管线（boot 清单注入走这里）

鉴权约定：dsh 没有全局鉴权中间件 —— 每个插件各自负责自己路由的信任检查。宿主自己的示范：/api 由 client-connection 注册并过 DNS-rebinding 信任栅栏（非同源/非信任 host 403，特权方法钉死 loopback）；静态前端 claim fallback 席位；插件自定义 API 的典型形状是「自定前缀 + POST 变更做 Origin/sec-fetch-site 校验」：

// dsh-wecom /dsh-wecom/api（plugins/dsh-wecom/src/http-api.ts:8-58）
webServer.register({ kind: 'prefix', path: '/dsh-wecom/api', handler })
// GET 只读接口开放；POST（restart 等）isTrustedMutationRequest：
//   sec-fetch-site 必须 same-origin 且 Origin 严格等于 managementOrigin
// 响应统一 no-store / no-referrer / nosniff

Web 客户端扩展：client bundle 与 slots

插件的浏览器侧如何被宿主发现？（packages/client/modules/src/index.ts）

  1. 插件包在 package.json 声明 dsh.client: { platform: 'web', inject: […], immediately? } 且 exports["./client"] 存在；
  2. 宿主 clientModules 服务（inject: webServer + loader）扫描 loader entries，把每个 client bundle 暴露为 /plugins/<pkg>/client.js?rev=<sha1前12>（内容寻址缓存穿透）；
  3. tapIndex 把入口清单 { rev, entries: […] } 注入 index.html 的 window.__DSH_BOOT__；
  4. 浏览器 shell 内核拉取执行 —— client 模块同样是 cordis 插件形状：export const inject = ['slots'] + apply(ctx: ClientContext)，跑在浏览器里的另一个 cordis 上下文。

浏览器侧的服务面由 dsh-client-runtime 提供：ctx.slots（SlotRegistry）、ctx.conversation（输入区）、ctx.sessions / ctx.workspaces、ctx.layout。槽位契约经 SlotMap 声明合并扩展，种类 single|list|keyed|chain、作用域 root|session-maybe|session。我们插件用过的槽位：

槽位类型用途我们的用法
settings.plugins.tablist插件设置页里的一个 tabreading / obsidian 的设置面板（含版本条）
sidebar.footer.actionlist侧栏底部动作按钮wecom 面板入口、reading 书本按钮、obsidian 工作台
shell.overlaylist全屏浮层wecom / reading / obsidian 的工作台 portal
conversation.input.left / .docklist / session输入区左侧 / 停靠区file-attachment 的回形针按钮与附件 dock
sidebar.workspacessingle侧栏工作区区obsidian 的 VaultBrowser
conversation / conversation.session / details—对话区相关obsidian NotePanel 按会话状态动态选位

工作台叠加范式（reading/obsidian 共用）：createPortal + 在宿主 DOM 探测 [data-phase] 锚点 + 纯函数几何模块（可单测）—— 不修改宿主布局代码，宿主壳对插件零感知。

skills — 技能 provider 注册表

ctx.skills.registerProvider((control) => provider)（packages/skill/skill/src/index.ts:391），rank 越低越优先。dsh-obsidian 在全局层注册一个 provider（rank 300），实例经 setStore 跟随当前 vault —— 「全局注册、闭包换库」，vault 切换时调宿主 invalidate() 触发重列，技能集合动态跟随工作区而不重复注册。

串起来：一个回合的流水线

turn/start
  认领下一步输入 + 一条排队消息
  组装 prompt sections + tool schemas
  → agent/pre-step      拒绝 | 改写 enter(messages)     [waterfall —— 决定模型看到什么]
     step/start
     追加 user/message（落日志）
     从日志投影模型历史 deriveMessages()
     agent/request → llm/stream → assistant/chunk* → assistant/message
     tool/call* → tools/pre-execute → tools/execute → tools/post-execute → tool/result*
     step/end
  → agent/turn-stopping                                    [serial，无 next()]
turn/end

turn/*、step/*、user/message、assistant/*、tool/* 是持久会话事件；agent/pre-step、agent/request、llm/stream、tools/* 是活的扩展点（waterfall，必须调 next() 委托）。dsh-wecom 的 ask_user_question 卡片路由正是挂在这个体系上：宿主的 ask_user_question 工具在 agent/pre-step 读「本轮触发消息」的通道路由，把提问转给对应通道的 provider。
