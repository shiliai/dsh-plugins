集成机制：插件如何被安装、声明与更新

dsh 侧的机制（bundle/profile 双清单、安装对账、allowBuilds）× 我们仓库侧的实践（monorepo 子目录包、updater、bootstrap）。这一页解释我们 AGENTS.md 里每条纪律的「为什么」。

两个概念、两个清单：bundle 与 profile

官方纪律（docs/user/develop/basic/publish.md）A bundle is what you author and distribute; a profile is what a user boots with dsh --profile <name>. Nothing is both.
Bundle（我们写的）Profile（用户侧的）
是什么npm 包，携带一个配置层$DSH_HOME/profiles/<name> 目录，一份可运行的组合
清单"dsh": { "bundle": { "patch": "./cordis.patch.yml" } } —— 回答「这个包贡献什么」"dsh": { "profile": { "bundles": […] } } —— 回答「哪些 bundle 按什么顺序组合」
谁维护插件作者dsh plugin 自动维护（用户永远不手写）
我们的实例plugins/dsh-wecom/package.json + cordis.patch.yml~/.local/dsh_home/profiles/web/package.json

没有 dsh.bundle 声明的包也能装，但只作为普通依赖：dsh 会警告且不激活任何层 —— 这种格式留给「被插件包 import 的库」。

bundle 的 patch 文件：insert 即安装

我们 5 个插件的 cordis.patch.yml 都是同一个模式 —— insert 一行、声明 inject、给默认配置（!!js 读环境变量）。对比：

插件injectpatch 里的关键默认值安全姿态
dsh-wecomtools, agents, agentDefaultModel, agentPresets, sessions, webServerbotId/botSecret ← process.env；三张白名单默认空；authWatchdog 默认开启开箱即安全：零授权即零访问
dsh-remotewebServermode/origin/socket/state 全部 ← DSH_REMOTE_* 环境变量；另有 2 行目录选择器能力替换 + 把内置 auto 选择器 disabled: true远程场景不暴露宿主全盘路径
dsh-readingwebServerdataDir ← READING_DATA_DIR 或 null（走 env/默认链）API 响应永不外泄文件路径
dsh-obsidianwebServer, tools, skillsvaultRoot ← process.cwd()（支持 cd <vault> && dsh web）；mutationOrigin ← env写操作 Origin 白名单 + symlink 监狱
dsh-file-attachmentwebServer纯限额默认值（25MiB/文件、10 文件/消息、24h TTL）0700/0600 落盘 + 同源校验

用户侧覆盖发生在 profile 的 cordis.patch.yml（后层胜，整行替换 config）。实机样本：覆盖 dsh-wecom 白名单时必须连 botId/botSecret 一起复述 —— 注释里就写着「a patch replaces the WHOLE row config」。

安装契约：GitHub monorepo 子目录

# 1. 授权构建（pnpm ≥10 拒绝 git 依赖的 prepare 脚本；两种 Git source 归一化都要 trust）
dsh plugin --profile web config set --location=project --json allowBuilds \
  '{"@dsh-plugins/dsh-wecom@git+https://github.com/shiliai/dsh-plugins.git":true, …}'
#   ↑ 对 git+ssh 归一化形态再写一条同样的键（完整可复制的 allowBuilds JSON
#     见根 README「Install from GitHub」一节）

# 2. 安装（pnpm 的 git-hosted specifier：克隆仓库，#path: 指向 monorepo 子目录）
dsh plugin --profile web add 'github:shiliai/dsh-plugins#path:/plugins/dsh-wecom'

# 3. 重启 profile 生效

整条链路的关键节点：

  • dsh 对 spec 零特殊处理：原样进 pnpm。#path: 是 pnpm 的子目录语法；dsh 只在安装后做对账（按真实包名 @dsh-plugins/dsh-wecom 追加进 dsh.profile.bundles，与命令行 spec 解耦）。
  • git 安装拉的是源码：pnpm 装完运行该包的 prepare 脚本自举构建 —— 所以我们的每个插件包必须有自包含的 prepare（不能假设兄弟 monorepo checkout 存在），产物覆盖 main/types/exports/bin 声明的全部文件。
  • allowBuilds 是信任声明：等于「允许在安装期于本机执行这个包的代码」。官方建议同时 pin commit（github:you/pkg#<sha>）防止后续 push 静默改变运行内容。

更新：为什么必须走仓库 updater

pnpm 的盲区：普通 pnpm outdated 检测不到 Git 依赖有了新 commit（它比的是版本 spec，而 github:…#path: 没有版本号）；本地 link:/tarball 安装更是完全无法被发现。所以更新走自研 updater，经 dsh 的 dlx 执行：

dsh plugin --profile web --config.dlx-cache-max-age=0 dlx \
  'github:shiliai/dsh-plugins#path:/scripts/dsh-plugin-updater' check|update @dsh-plugins/dsh-wecom
机制解决什么
--config.dlx-cache-max-age=0dlx 默认复用缓存的 Git 快照；置 0 强制 pnpm 每次解析 updater 的当前 revision —— 否则 updater 本身可能跑旧逻辑
GitHub Contents API 比对读仓库内各插件 package.json 的最新 SemVer，与已安装版本严格比较；本地比 GitHub 新（降级）直接报错 —— 回滚必须用更新前留存的本地 tarball
迁移状态机依赖 spec 不指向 GitHub source 时判 migration-required，update 时先做一次性迁移 —— 解决「本地/link:/tarball 安装无法被发现」
configureBuildTrustupdate 前自动为 git+https 与 git+ssh 两种归一化形态写 allowBuilds —— 这就是 AGENTS.md「Build trust 必须覆盖两种归一化」的出处
收敛复检update 后重新 check，不收敛即抛错

bootstrap：跨机器一键引导

scripts/dsh-bootstrap 把上面所有契约串成幂等的五阶段：ensure-dsh → credentials（原子写 .credentials.yaml，mode 600）→ settings（便携模板物化为本机文件，绝不覆盖用户真实配置）→ plugins（先 ensureBuildTrust，安装一律走 dsh plugin add）→ update（先升 dsh 并冒烟验证，再升插件）。两个值得记住的设计：

  • 先升宿主再升插件的顺序有注释点明原因：插件若对着更新的 core 解析，可能让 Web 出现重复的私有 scope 符号、会话无法绑定；
  • 入口的 assertProfileSafe 拒绝 npm/pnpm 双锁文件与 profile 私有 DSH core 包的混合状态。

重启安全协议（TOOL_OUTCOME_UNKNOWN）

我们 AGENTS.md 的第一条纪律背后是 Harness 的一条不变量：tool/call 先于 tool/result 落盘。如果在一个跑在 DSH 进程内的工具调用里杀掉/替换该进程，对应 result 永远缺失，会话恢复时就会出现 TOOL_OUTCOME_UNKNOWN。所以正确姿势是两阶段：

  1. 部署命令跑完并持久记录结果；
  2. 由外部 supervisor / 独立终端重启 DSH，在新请求里验证健康与会话恢复。

dsh-remote 的安装脚本把这个纪律工程化成 trap 式两阶段提交（失败自动还原）；wecom 面板的 /restart 只重建插件桥、绝不动 DSH 本体。

四种集成模式（按侵入度递增）

① 纯旁路（transport）

只消费 webServer，自建 API + client UI，不碰 agent。代表：dsh-remote、dsh-reading、dsh-file-attachment。适合「给 Web UI 加一块独立功能」。

② 提供工具（capability）

在 ① 之上注册 ctx.tools，让模型获得新能力。代表：dsh-obsidian 的 8 个笔记工具、wecom 的出站推送。要点：工具自带安全边界（白名单/围栏/乐观锁）。

③ 驱动回合（driver）

成为「用户入口」：外部消息 → agents.create/resume → agent.followup → 读会话事件生成回复。代表：dsh-wecom。要点：会话映射、生命周期回收、与 web 通道共存。

④ 接管交互（interaction）

把宿主的交互原语路由到自己通道：注册 userQuestions 通道 provider，ask_user_question 以企微模板卡下发、答案作为工具结果回来。代表：dsh-wecom。这是最深的集成形态。

注意四层的共同点：没有一个改过宿主一行代码 —— 全部通过 insert 行、inject、事件与服务注册完成。dsh-remote 对宿主 webServer 内部 socket 的唯一「接触」也只是一个防御性的错误吸收器（且被 AGENTS.md 列为每个 release 必须保留的行为）。代码层面的接口契约与设计模式另见接口与模式专页。
