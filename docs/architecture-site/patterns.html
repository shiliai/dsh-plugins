接口与设计模式

两部分：主要接口设计（源码里的关键 TS 契约，保留原注释精髓）与 设计模式目录（dsh 反复使用的手法，每个配最小代码与我们插件的印证）。接口均摘自 deepseek-harness@8534614a1，有删节。

一、主要接口设计

1. Plugin.Base —— 插件元数据契约

一切插件（官方的与我们写的）共享的五个元数据字段。这是整个体系最小的接口，也是「一切皆插件」的字面落点。

// vendor/cordis/lib/types/registry.d.ts:52-63
export type Plugin<T = any> = Plugin.Function<T> | Plugin.Constructor<T> | Plugin.Object<T>

export namespace Plugin {
  interface Base<T = any> {
    /** 展示名：fiber 诊断与 logger 名 */
    name?: string
    /** Standard-schema 校验器：插件启动前校验 config（dsh 用 Schemastery）*/
    Config?: StandardSchemaV1<any, T>
    /** 所需服务：全部可用时才加载 */
    inject?: Inject
    /** 本插件提供的服务名（Service 基类与 loader 都读它）*/
    provide?: string | string[]
    /** 声明消费哪些服务的 intercept 配置 */
    intercept?: Dict<boolean>
  }
}

2. Service 基类 —— 构造即注册

// vendor/cordis/lib/types/service.d.ts:9-54（节选）
export declare abstract class Service<out T = never> {
  protected ctx: Context
  /** 特殊静态符号键 */
  static readonly init: unique symbol    // 构造后运行的实例方法
  static readonly check: unique symbol   // 可用性谓词，传给 ctx.provide()
  static readonly invoke: unique symbol  // 可调用服务的函数体（如 ctx.logger()）

  /** 服务名 */
  name: string

  /** 以 name 注册进当前上下文；随所属 fiber 卸载自动注销 */
  constructor(ctx: Context, name: string)
}

关键设计：super(ctx, name) 一行同时完成「存储依赖」与「注册自己」—— 服务的生命周期由提供它的 fiber 拥有，没有独立的注销调用。

3. ToolDefinition —— 规范值与展示分离

工具接口最值得注意的是：execute 返回规范 JSON 值，模型可见内容由 output.render 纯函数投影，UI 卡片由 presentCall/presentResult 纯函数声明 —— 数据、模型视图、人视图三者分离。

// packages/core/tools/src/index.ts:210-288（节选）
export interface ToolOutputDefinition {
  /** 规范值的 JSON Schema：每个成功返回都会被校验 */
  readonly schema: JsonSchemaNode
  /** 纯函数投影：参数 + 规范值 → 模型内容 */
  render(args: unknown, value: JsonValue): ContentBlock[]
}

export interface ToolDefinition extends ToolSchema {
  readonly output: ToolOutputDefinition
  /** 返回 output.schema 声明的规范值；异步工作必须观察 exec.signal */
  execute(args: unknown, exec: ToolRunContext): Promise<unknown>
  /** 协作式超时预算（毫秒）。绝不发给模型 —— schemas() 只暴露 name/description/parameters */
  timeoutMs?: number
  /** 纯同步分类器：能否与兄弟工具调用并行（只有 true 才加入并行组）*/
  isConcurrencySafe?(args: unknown): boolean
  /** PENDING 态的 UI 渲染意图。纯函数：直播流与会话回放都会调用，只许依赖 args */
  presentCall?(args: unknown): ToolCallView | undefined
  /** COMPLETED 态的 UI 渲染意图。同样的纯函数/重放安全约束 */
  presentResult?(args: unknown, result: ToolResult): ToolResultView | undefined
}

二、设计模式目录

dsh 没有发明新名词，但它把一批经典模式用得非常一致。按「容器与组合 → 能力与扩展 → 数据与可靠性 → 面向模型」四组整理，每组模式给出：dsh 在哪用、最小代码、我们的插件哪里印证。

组 A · 容器与组合

A1. IoC 容器 + 服务定位器（依赖倒置）

手法：能力不通过 import 具体实现获得，而是以稳定 key 挂在 ctx 上按需定位；依赖方向由 inject 声明，装载顺序是数据不是代码。

export const inject = ['tools', 'webServer']   // 声明
export function apply(ctx: Context) {
  ctx.tools.register(…)                          // 定位使用
}

印证：reading 只 inject webServer，wecom inject 六个服务 —— 依赖面即集成面。

A2. 声明合并做类型扩展点

手法：框架的 Context、Events、宿主的 SlotMap、SessionEventMap 全是 interface，插件用 TypeScript declaration merging 无侵入地补类型 —— 扩展点即类型。

declare module '@deepseek-ai/cordis' { interface Context { tools: ToolRuntime } }
declare module '@deepseek-ai/cordis' { interface Events { 'my/evt': (p: P) => void } }
declare module '@deepseek-ai/dsh-client-ui-slots' { interface SlotMap { … } }
declare module '@deepseek-ai/dsh-session' { interface SessionEventMap { … } }

印证：我们插件里的 dsh-shims.d.ts —— 出树工程拿不到宿主编译单元内的增广，就自己重建消费面的最小声明。这套体系里「类型从哪来」是有明确答案的：宿主发 .d.ts + 消费方声明合并。

A3. 洋葱中间件（around-dispatch / waterfall）

手法：拦截点不是回调钩子，而是 waterfall 事件 —— 监听者收 (...args, next)，调 next() 委托、不调即短路。拦截与网关语义内建在派发机制里。

// dsh-base 的 approval 策略监听 tools/pre-execute（示意）
ctx.on('tools/pre-execute', (exec, next) => {
  if (!policy.allows(exec.name)) return { decision: 'deny' }  // 不调 next = 短路
  return next()                                                // 委托下游
})

印证：宿主的 ask_user_question 工具在 agent/pre-step 读触发消息路由 —— 我们没有写任何「钩子注入」代码，路由信息穿透完全靠这个机制。

A4. RAII / Effect 系统

手法：一切注册都是 effect，持有 disposer；卸载逆序回收。资源管理从「记得清理」变成「注册即登记清理」。

ctx.effect(() => {
  const timer = setInterval(sweep, interval); timer.unref?.()
  return () => clearInterval(timer)      // 卸载时运行
})
// 顺序敏感时用生成器 effect：yield 的 disposer 逆序执行、中途抛错已 yield 的也回滚
ctx.effect(function* () { yield a; yield b })

印证：file-attachment 的 TTL 定时器 unref() + ctx.effect 注销；wecom 面板 /restart 后旧监听无残留。

A5. 声明式组合 / 配置解释器（整行替换）

手法：产品 = 补丁层对空根的求值。补丁按 id 寻址、整行替换、后层胜 —— 把「防幽灵默认值」做进语义。

# 实机 ~/.local/dsh_home/profiles/web/cordis.patch.yml（节选）
- id: dsh-wecom          # 按 id 寻址任何一层（包括官方 bundle）的行
  config:                # 整行替换：必须复述 botId/botSecret
    botId: !!js process.env.WECOM_BOT_ID ?? ''
    allowChats: ['*']

A6. 命令行即服务

手法：launcher 把 argv 冻成 cmdlineArgs 服务；任何插件都能声明自己的 commander 程序解析它、再 provide 一个服务；依赖行用 !!js ctx.该服务.port ?? 默认 消费 —— flag 是最高优先级的临时配置，且 --help 时 provider 不发布服务、依赖行自然不激活。

// 宿主 web-startup（packages/bundle/web-app/src/startup.ts）；dsh-web-app 的 cordis.patch.yml：
- id: webserver
  inject: [webStartup]
  config:
    host: !!js ctx.webStartup.host ?? '127.0.0.1'
    port: !!js ctx.webStartup.port ?? 3080

组 B · 能力与扩展

B1. 端口-适配器三角色（能力缝）

手法：可替换能力拆成三个包角色 —— Definition（抽象类/接口）、Provider（实现，可换）、Consumer（常是模型工具）。消费者与提供者都只依赖 Definition 的类型。换 Provider = 换产品行为。

session-persistence（Definition）← session-persistence-jsonl / -sqlite（Provider）
shell（Definition）              ← bash-local / pwsh / sandbox（Provider）
skills（注册表）                  ← dsh-obsidian 的 vault 技能（我们加的 Provider，rank 300）

B2. 工厂 + 事务性 setup

手法：agent 创建的 setup/commit/rollback 三段（见上文接口 4）—— 「观察者永远看不到配置了一半的世界」。复杂初始化的原子性由框架保证，插件只写 setup(agentCtx)。

印证：wecom 的 ensureAgent 在 setup 里装模型选择 + mount preset —— 若 mount 失败，整个 agent 创建回滚，聊天队列收到错误而不是拿到半成品 agent。

B3. 通道 Provider 路由（Strategy + Registry）

手法：同一个抽象（提问交互）按「通道」注册多个实现，请求携带可信路由决定走哪个。

userQuestions.registerProvider('wecom', { ask })   // 我们的通道实现
userQuestions.registerProvider(webProvider)          // 浏览器默认 —— 同进程共存
// ask() 按 route.channel 分发；无 provider → NO_PROVIDER_FOR_ROUTE

B4. Symbol.for 共享进程级注册表

手法：跨包协作的「暗信道」—— 双方用同一个全局符号键拿同一个注册表，不需要共同 import 一个包。

// 宿主 packages/interaction/user-questions/src/index.ts:35
const registry = /* Symbol.for('@deepseek-ai/dsh-user-questions/interaction-route-registry') */
// 我们 plugins/dsh-wecom/src/questions.ts:58 —— 刻意复刻同一键，共享同一注册表
routeUserMessage(msg, { channel: 'wecom', destination: chatKey })  // 写
// 宿主 ask_user_question 在 agent/pre-step 读 —— 跨包语义打通，零协议改动
代价与纪律这是强耦合的进程内约定：宿主改键名/结构就会断。所以 wecom 同时保留了能力探测（supportsRouting === true 才注册）与跨版本事件源探测链 —— 用「暗信道」时必须配套「握手」。

组 C · 数据与可靠性

C1. 事件溯源 + 投影（Event Sourcing）

手法：会话 = append-only 事件日志；UI、模型历史、fork、恢复全是投影（deriveMessages()）。铁律：model-visible means logged，带运行时不变量断言。

// dsh-wecom 的回合摘要 = 从事件后缀投影（plugins/dsh-wecom/src/frame.ts:16-42）
const result = summarizeTurn(sessionEvents.slice(firstSeq), …)
// 与浏览器看到的是同一份事实 —— 不存在「机器人回复和网页不一致」

C2. 每键串行队列（per-key promise chain）

手法：并发控制的最小实现 —— 按资源 key 串行、跨 key 并行，settle 后清理自身。

// wecom 的聊天队列（index.ts:1223-1275）与 obsidian 的 mutate()、reading 的 state-store 写链
const prev = queues.get(key) ?? Promise.resolve()
const next = prev.then(run).finally(() => { if (queues.get(key) === next) queues.delete(key) })
queues.set(key, next)

C3. 乐观锁

手法：把「并发写冲突」变成结构化 409，而不是 last-write-wins。

// obsidian 写笔记：替换必须带 expectedModifiedMs（mtime）；技能 revision = 内容 sha256
if (exists && expectedModifiedMs === undefined) throw NOTE_EXISTS
if (stat.mtimeMs !== expectedModifiedMs) throw NOTE_CONFLICT

C4. Stale-while-revalidate + 内容寻址缓存

手法：读旧值兜底、成功异步回写（reading 的 remote-cache）；静态资源以内容哈希做缓存穿透（宿主 /plugins/<pkg>/client.js?rev=<sha1前12>）。

// plugins/dsh-reading/src/remote-cache.ts + wallabag-adapter.ts
try { value = await fetchRemote() } catch { return readCache(key) ?? rethrow }  // 兜底
queueWriteCache(key, value)                                                        // 异步回写

C5. 两阶段提交 + trap 回滚

手法：跨系统变更（安装/轮换/升级）先全部准备、后原子提交；任何阶段失败回滚到一致态。

# install-dsh-remote-instance.sh：committed=true 之前任何失败触发 restore()
trap '[ "$committed" = true ] || restore' EXIT
…
atomic_rename("$tmp", "$state")   # dsh-remote 的 state rotate：rename 即提交点
committed=true

C6. 看门狗（降级分类 + 冷却）

手法：对「外部授权/连接的静默劣化」显式建模 —— 观察事件流 → 分类（auth/connection）→ 持续时间过滤（minDowntime 滤抖动）→ 冷却（alertCooldown 防风暴）→ 多目的地告警。

// plugins/dsh-wecom/src/watchdog.ts：只提取错误码，永不携带消息体
classifyError(err)  // → 'auth' | 'connection'
degraded ≥ minDowntimeMs(120s) 且 距上次告警 ≥ alertCooldownMs(1h) → fireNow()

组 D · 面向模型的模式

D1. 文本即协议

手法：给模型新能力时，优先考虑「降维成 prompt 里的结构化文本」而不是新消息类型 —— 模型已有的工具（读文件）成为执行器。

// file-attachment 的引用块；reading 的 [Reading item]；obsidian 的 [Obsidian context]
[Attached file: report.xlsx]
type: application/vnd.…sheet
size: 48213 bytes
uri: file:///…/attachments/tmp/…-report.xlsx   ← agent 用既有工具按 URI 自取

为什么：不做 RAG、不改消息协议、不碰 session 服务 —— 三个插件的「内容进上下文」收敛为同一个低侵入动作（往 ctx.conversation.input 草稿追加文本块）。

D2. 展示与数据分离（工具的三重视图）

手法：execute 产出规范值 → output.render 投影给模型 → presentCall/presentResult 声明 UI 卡片。三个视图都是纯函数（重放安全），数据只有一份规范值。

execute(args) → { ok: true, message: '…' }      // 规范值（唯一事实）
output.render(_a, v) → [{ type: 'text', text: … }] // 模型视图
presentResult(a, r) → { card: … }                  // 人视图（可缺省）

印证：obsidian 的 obsidian_write_note 新建渲染 diff 卡片、替换渲染 write 卡片 —— 都是 presentResult 的纯函数分支，不碰执行路径。

D3. 默认拒绝的安全默认（deny-by-default）

手法：能力面（白名单、目录、出站目标）空 = 拒绝；* 必须显式写出来才放行全部。与「fail loud」配套：坏配置在加载期报错，而不是运行期降级。

// wecom 三张白名单；remote 网关的 LOOPBACK_ONLY_METHODS；宿主 web-startup 拒绝 --host 0.0.0.0
isAllowed(target, list) { return list.length > 0 && (list.includes('*') || list.includes(target)) }
