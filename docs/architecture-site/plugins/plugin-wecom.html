dsh-wecom：企微长连接机器人桥

把企业微信变成 dsh 的用户入口：每条企微消息 = 一个 agent 回合，对话记忆与会话管理齐全，ask_user_question 以模板卡路由回企微。这是五个插件里集成最深的一个 —— 驱动回合 + 接管交互两种模式都用上了。

v0.5.2 · inject: [tools, agents, agentDefaultModel, agentPresets, sessions, webServer]（另可选消费 userQuestions / sessionPersistence / workspaceRegistry）

一条消息的完整生命周期

  1. SDK 层：@wecom/aibot-node-sdk WSClient 负责 connect / 30s 心跳 / 无限重连（bot.ts:87-97）；
  2. 归一化：帧 → InboundMessage，以 botId:msgId 去重（10 分钟 TTL 有界缓存）；
  3. 鉴权：isInboundAuthorized —— 群聊双闸（allowChats 放行群 id 且 allowGroupSenders 放行 sender），单聊 allowChats 放行；未授权静默丢弃不回复；
  4. 队列：每聊天一个 Promise 队列（同聊天严格串行、不同聊天并行）→ evictIdle（idleChatMs 默认 30min、maxLiveChats 默认 100）；
  5. /命令短路：/help /new /cd /pwd /agent /status /sessions /attach /detach 直接回复，不开 agent 回合；
  6. 开回合：ensureAgent 拿活句柄 → 打「🤔 思考中…」流式占位 → routeUserMessage(msg, {channel:'wecom', destination: chatKey}) 写入进程级路由注册表 → agent.followup(userMessage) + agent.whenIdle() + sessions.flush()；
  7. 摘要回复：summarizeTurn(事件, firstSeq) 从会话事件后缀取最后一段 assistant 文本，turn/end 的 reason 决定 ok —— 与浏览器看到的是同一份会话事实；同一 streamId 原位替换占位气泡。

会话模型：epoch、resume 与绑定

  • 会话 id 公式：wecom:<botId>:<chatType>:<chatId>[:epoch]:<generation>。默认带进程级 epoch（randomUUID）—— 重启即新纪元，从不 resume；resumeSessions: true 是显式 opt-in，去掉 epoch 使 id 跨重启稳定，恢复时扫 sessionPersistence.listSnapshots() 找本插件命名空间下的最大 generation。
  • web 会话绑定：/attach//sessions <id>//new 把聊天绑到既有 web 会话 —— 浏览器与机器人共享同一份对话日志。镜像双向：插件订阅全局 session/event 观察浏览器侧写入并推回企微；wecom→web 的写入在 followup 之前打消息 id 自标记防回环。
  • 绑定持久化的顺序性：/new /attach /detach /sessions 全部 await 落盘后才回复，消灭「重启复活已 detach 的会话」竞态。
  • 一 live-agent 约束：目标会话正在浏览器里活 agents.get() 命中时，绑定后首条消息会报 bound session is currently live in the browser —— 这是宿主注册表的诚实反馈，不是 bug。

问题卡片：最精妙的宿主协作

agent 在回合里调用宿主的 ask_user_question 工具时，提问如何「长」在企微里？

  1. 宿主 dsh-user-questions 服务支持多 provider：registerProvider(channel, provider)，ask() 按请求上的可信路由选 provider；
  2. 插件刻意本地复刻宿主同一套 wire 类型与同一个 Symbol.for 注册表键，于是 routeUserMessage 写入的路由能被宿主读到 —— 跨包协作靠进程内约定，不改宿主消息格式；
  3. 启动时 registerProvider('wecom', { ask })（校验 supportsRouting === true）—— 与浏览器的 web 通道同进程共存，企微消息开启的回合其提问必然回到企微；
  4. 下发模板卡（≤5 选项，不可卡片化则发编号文本并释放回合）→ 用户点选 → 四重校验（路由通道 / 目的地聊天 / live agent 归属 / 本轮授权 sender）→ 答案作为 ask_user_question 的工具结果回到同一会话 → 卡片置灰显示所选项。10 分钟超时。

工具与 HTTP API

面内容安全
agent 工具 wecom_send_message主动推送 Markdown 到单聊/群聊（≤20000 字符）outboundAllowChats 默认拒绝；串行执行

POST /dsh-wecom/api/restart只重建企微桥与长连接（不动 DSH —— 重启安全协议）sec-fetch-site same-origin + Origin === managementOrigin
GET/POST /dsh-wecom/api/wecom-cli-update对比/安装 @wecom/cli 最新版同上

安全设计清单

  • 三张默认拒绝白名单：allowChats / allowGroupSenders / outboundAllowChats，空 = 拒绝，* 仅显式放行全部单聊；
  • 路径围栏：resolveAllowedDirectory 先 realpath 再前缀匹配，同时封死 ..、绝对路径逃逸与 symlink 逃逸；/cd、/new、ensureAgent 全过这道闸；
  • 日志卫生：机器人层日志只含 chatId/msgId/字节数，绝不含消息体与 token；SDK debug 日志（会序列化帧体）被强制丢弃；启动失败栈先替换 secret 再截断；
  • authWatchdog：企微数据权限是 90 天定期授权、到期事件不走 WS 长连接 —— watchdog 观察连接生命周期分类降级（auth/connection），持续 ≥2min 且冷却 ≥1h 才告警（日志 + 常驻 bot 消息 + webhook），只提取错误码、永不携带消息体；主动续期扩展点 notifyDataPermissionExpiry 供指令回调接收器调用。

值得带走的设计点

  • 跨宿主协作的最小协议：复刻 wire 类型 + 共享 Symbol.for 注册表键 —— 不 fork 宿主、不改协议；宿主升级时只需复验结构兼容（插件有跨 dsh-session 版本的事件源探测链 session.events → snapshotEvents() → ownEvents() → session.log）。
  • 错误追踪分层：低层日志只落 safeErrorKind（防泄漏），「需要人诊断」的回合失败层才带 errorMessage + errorStack 落 error 级 —— 把「用户截图排查」变成「看日志排查」。
  • 重启安全：所有生命周期操作入串行队列、四阶段启动（create-bot → create-bridge → optional-capabilities → connect）失败产生稳定诊断码 STARTUP_<STAGE>；插件级 restart 读不到新的父进程环境，WECOM_BOT_* 改动必须重启 profile。
