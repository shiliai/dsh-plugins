dsh-file-attachment：文本即协议的本地附件

给纯文本模型的会话加「本地文件附件」。核心洞察：附件可以降维成 prompt 里的一段结构化文本 —— 文件名 + media type + 字节数 + 绝对 file:// URI，由 agent 自行决定用宿主本地工具还是 MCP 工具去读。最小的代码量换一个完整的产品能力。

v0.1.0 · inject: [webServer] · 零 agent 工具（spec 明确列为 Non-goal）

与宿主 attachment 体系的关系：正交，不是桥接

宿主 ctx.attachments本插件
定位持久图像 seam任意类型文件的临时附件
内容PNG/JPEG/WebP/GIF，sha256 内容寻址，写入会话事件的 ImageAttachmentRef任意 media type，落盘 $DSH_HOME/attachments/tmp
进入模型的方式原生 image block纯文本引用块（模型读 URI 后用工具拉取）
生命周期持久、无 GC24h TTL 定时清理

两者不 inject 彼此、不产生 image block、不碰能力元数据 —— 只在「共用 $DSH_HOME/attachments 目录约定」上相遇（宿主 v1/objects，插件 tmp）。这是 dsh 生态里的典型判断题：什么时候不该复用宿主既有服务 —— 当威胁模型与生命周期完全不同时，旁路扩展比强行桥接更干净。

「文本即协议」的引用块

[Attached file: quarterly-report.xlsx]
type: application/vnd.openxmlformats-officedocument.spreadsheetml.sheet
size: 48213 bytes
uri: file:///Users/chris/.local/dsh_home/attachments/tmp/3f2a…-quarterly-report.xlsx

上传成功即由 client 把引用块写进会话输入草稿（inputActions.setDraft）。模型看到的是纯文本，它已经有了读文件的工具 —— 插件不需要教会模型任何新东西。

HTTP API 与存储

端点用途
GET /limits限额预检（25MiB/文件、10 文件/消息、100MiB/消息、24h TTL）
POST /upload{files:[{name,mediaType,data:canonical base64}], existingFileIds}；existingFileIds 支持「草稿里已有附件再追加」的批量一致性校验
DELETE /file取消附件（删文件 + 摘引用块）

存储细节（file-store.ts）：目录 0700、文件 0600、wx 独占创建；<uuid>-<清洗后显示名>；canonical base64 严格校验（重新编码必须与输入一致）；fileId 正则 + resolve 后不逃出 root 双检；saveBatch 任一失败回滚已写文件；TTL 按 mtime 清理，定时器 unref()。

client 侧的完整闭环

  • 两个槽位：conversation.input.left 回形针按钮、conversation.input.dock 附件 dock；
  • 输入方式：文件选择 / 拖放 / 剪贴板粘贴（document 捕获级 paste，同时读 clipboardData.files 与 items 按指纹去重）；
  • 草稿与 dock 双向同步：草稿里引用块被用户删掉 → 同步删附件记录；删除按钮 → API 删文件 + 从草稿摘除引用块；
  • 草稿附件状态按 session 隔离（draft-store）。

值得带走的设计点

  • Non-goals 是 spec 的一部分：不改模型能力元数据、不产生原生图像 block、不自动调 MCP 工具 —— 三个「不做」保住了正交性，也把实现压到最小。
  • 写操作的 Origin 策略居中：Origin 必须存在且非 null，匹配 allowedOrigins 或与请求 Host 一致 —— 比 reading（无 Origin 放行）严、比 obsidian（严格等于配置值）松，又一次按威胁模型定制。
  • 限额即配置：root/allowedOrigins 刻意不在 patch 里给默认值，留给用户层覆盖 —— 「bundle 给安全默认，用户层给部署特化」。
