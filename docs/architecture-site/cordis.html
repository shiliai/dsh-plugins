Cordis：插件容器模型

dsh 之下是 vendored 的 Cordis（源码在 vendor/cordis，发布为 @deepseek-ai/cordis）。理解 dsh 先理解 Cordis —— 官方入门是 docs/cordis-primer.md（44 行），本页把它与源码实证合并。

五个核心思想

概念含义源码依据
插件 = Service 插件是一个实现 Plugin 形状的模块：函数形 / 对象形 / 类形三种（函数形最常用，类形用于「向别人提供服务」）。 vendor/cordis/lib/types/registry.d.ts:48；Plugin.Function | Plugin.Constructor | Plugin.Object
Context = 服务仓库 Context 是运行时代理，服务以稳定的 ctx.<key>（如 ctx.tools、ctx.sessions）对外暴露；消费方按 key 找服务而不是 import 具体实现。 vendor/cordis/lib/types/context.d.ts:36-40；类型由声明合并挂上：declare module '@deepseek-ai/cordis' { interface Context { tools: ToolRuntime } }
inject 声明依赖 插件列出的必需服务全部就绪后才会加载 —— 装载顺序是数据（服务需求），不是手工引导序列。 vendor/cordis/lib/types/registry.d.ts:56-58
类型化事件 服务间通信走事件总线，四种派发模式（见下）；事件名经 TS 声明合并获得类型，dsh 用 @mode JSDoc 标注把声明与派发点交给生成目录校验。 vendor/cordis/lib/types/events.d.ts:25；docs/cordis-primer.md:31-39
注册即可逆 effect 一切注册（工具、监听器、路由、定时器）都装入当前 Fiber，卸载时逆序执行 disposer。reload 与 teardown 因此可预测。 vendor/cordis/lib/types/fiber.d.ts:41-51

插件的三种形态

// ① 函数形（dsh 插件最常用；我们的 5 个插件全是这种）
export const name = 'dsh-wecom'
export const inject = ['tools', 'agents', 'sessions', 'webServer']
export interface Config { logLevel?: string }
export const Config = Schema.object({ logLevel: Schema.string().default('info') })
export function apply(ctx: Context, config: Config) { /* 注册能力 */ }

// ② 对象形
export default { name: 'x', inject: ['tools'], apply(ctx) { /*…*/ } }

// ③ 类形 —— 提供服务给其他插件时用
export default class MetricsService extends Service {
  static inject = ['llm']
  constructor(ctx: Context) { super(ctx, 'metrics') // 立即 ctx.provide('metrics', this) }
  record(event: string, v: number) { /*…*/ }
}

loader 的 unwrapExports（vendor/loader/src/index.ts:193-201）做 ESM/CJS 互操作，所以命名导出和 default 导出都合法。插件元数据（Plugin.Base）共五个字段：name（诊断/日志名）、Config（Standard Schema 校验器，dsh 用 Schemastery，加载前校验并填默认值）、inject（必需服务）、provide（提供的服务名）、intercept（消费服务时的拦截配置）。

Fiber 生命周期状态机

每个已加载的插件实例拥有一个 Fiber（vendor/cordis/lib/types/fiber.d.ts:67-74）：

ctx.plugin(plugin, config) 返回 Fiber（可 await 等待加载完成，配置校验失败会 reject）；fiber.dispose() 卸载并等清理结束；fiber.update(config) 走 internal/update waterfall —— HMR 正是借这个口子介入的。清理语义上有一个容易踩的坑：多个异步 disposer 并发执行、无串行完成保证，顺序敏感的清理必须收进单个 ctx.effect() 里自己 await。dsh 标准写法是生成器 effect：

ctx.effect(function* () {
  yield disposerA  // 卸载时逆序执行；生成器中途抛错，已 yield 的也会回滚
  yield disposerB
})
// 真实用例：ToolRuntime 的注册回收 packages/core/tools/src/index.ts:951-971

事件系统：四种派发模式

模式等待？顺序返回值dsh 典型用法
emit否注册序观察无tools/result（冻结的终局观察）、session/event（追加流）
waterfall否注册序有（洋葱式）agent/pre-step（决定模型看到什么）、tools/pre-execute（allow/deny/ask）
parallel是并行无session/flush（持久化检查点）
serial / bail是 / 同步注册序首个非空值终止单决策事件，如策略短路

waterfall 是 around 中间件：监听者收到 (...args, next)，必须调用 next() 委托下游，不调用即短路（这正是拦截与网关语义的设计）。协作式监听者的惯例是改共享请求/决策对象后委托。dsh 的三条事件域（docs/architecture.md:53-61）：

  • Session 事件：turn/*、step/*、user/message、assistant/*、tool/* —— 追加进持久日志的事实；要观察它们监听 session/event 并检查 event.type（dsh-wecom 镜像 web 消息正是这么做的）。
  • Agent 事件（agent/*）：携带活的 Agent —— inbox、step、request、continuation，用于观察或拦截进行中的工作。
  • 能力事件（fs/*、tools/*、telemetry/*）：把策略与适配器挂到能力缝上，不 import 循环。

事件类型同样靠声明合并获得类型：

declare module '@deepseek-ai/cordis' {
  interface Events {
    'my-plugin/ready': (payload: { id: string }) => void
    'my-plugin/transform': (input: string, next: () => Promise<string>) => Promise<string>
  }
}

提供与消费服务

消费就是 inject + ctx.<key>；可选依赖则不进 inject、使用点 ctx.get('x') 判空降级。dsh 官方把这条称为插件的鲁棒性手段：可选服务（如 web profile 才有的 sessionPersistence）缺席时插件照常工作。

提供服务的完整契约（docs/user/develop/framework/service.md）：

  • super(ctx, name) 构造即 ctx.provide(name, this)，随 Fiber 卸载自动注销；
  • 用声明合并给 ctx 补类型：interface Context { metrics: MetricsService }；
  • 特殊静态符号：Service.init（构造后运行的实例方法）、Service.check（可用性谓词）、Service.invoke（可调用服务如 ctx.logger()）。

服务隔离（isolate）：cordis.yml 可以把同名服务隔离到不同 realm，让不同插件组看到不同实例 —— dsh 的 agent preset 机制整个建立在它上面（每个 preset 是一份 cordis.yml，按 preset 挂载为常驻 scope，agent 通过 scope 父子绑定加入组合，见 packages/preset/agent-presets/src/index.ts:1-21）。

三个加载器插件

包角色
@deepseek-ai/cordis-plugin-loader运行时插件树：持有 EntryTree，按 specifier import 模块、应用配置、维护运行中的插件图并随 entry 更新同步。核心 API：loader.create/update/remove/resolve/await/locate。
@deepseek-ai/cordis-plugin-include文件化的 loader 树：读 cordis.yml / patch YAML，变成 loader entries（可写回）；支持按 id 的 patches（config 覆盖 + insert 行）和 !!js 表达式。
@deepseek-ai/cordis-plugin-hmr热更新：watch 源文件、追踪模块图、清缓存、只重载受影响的 entry；框架级依赖变更时回退为进程重启。

!!js 的求值时机值得单独记住：解析期它只是 {__jsExpr} 节点；挂载期才在该行自己的 Fiber 上下文里求值（实现就是 with (ctx) { eval(expr) }，vendor/loader/src/config/utils.ts:5），且发生在该行 inject 的服务就绪之后。所以可以写 ctx.webStartup.port ?? 3080、process.env.WECOM_BOT_ID ?? ''、dshHomePath('sessions')。

为什么 HMR 是安全的因为「注册即可逆副作用」+「配置编辑 = 卸载旧实例再加载新实例」：改 profile 的 cordis.patch.yml 或插件源码，旧注册全部自动回收，新实例重跑 apply —— 不会残留旧实例的任何注册（docs/user/develop/basic/config.md:98-100）。
