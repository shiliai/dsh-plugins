从零写一个 dsh 插件

把前面所有机制串成一条可执行的路径。每一步都有官方文档或我们 5 个插件的源码作参照。

① 最小骨架（5 分钟能跑）

开发期根本不需要打包：一个 --patch 覆盖层指向本地模块即可（官方 docs/user/develop/basic/index.md）：

// scratch-plugin/src/my-plugin.ts
import type { Context } from '@deepseek-ai/cordis'

export const name = 'hello-plugin'
export function apply(ctx: Context) {
  console.log('[hello-plugin] plugin loaded!')
}
# scratch-plugin/cordis.yml —— 试装覆盖层（路径必须绝对）
- insert:
    - id: hello
      name: '/abs/path/to/scratch-plugin/src/my-plugin.ts'

# 源码仓库内：pnpm dsh web --patch ./scratch-plugin/cordis.yml
# 安装版：    dsh web --patch ./scratch-plugin/cordis.yml

改插件源码 → HMR 自动卸旧载新（一切注册自动回收）；改 cordis.yml → live 层重放组合。这就是「时空可组合」的开发体验。

② 配置：凡是两个部署可能想设不同值的，都必须是配置字段

import Schema from '@deepseek-ai/schemastery'

export interface Config { maxItems: number; verbose?: boolean }
export const Config: Schema<Config> = Schema.object({
  maxItems: Schema.number().default(50),   // 默认值写在 schema 上
  verbose: Schema.boolean().default(false),
})
export function apply(ctx: Context, config: Config) { /* config 已校验、已填默认 */ }
  • Config 必须是 Schemastery schema（Standard Schema 接口），不能是普通对象 —— 加载期校验失败即 fail loud；
  • 测试标准：cordis.yml 能否在不改代码的情况下改变这个值；
  • 环境变量不在代码里读 —— 在 cordis.patch.yml 里用 !!js process.env.FOO ?? 'default' 读（我们 5 个插件的统一做法：代码只认 config，patch 认环境）。

③ 给模型一个工具

export const inject = ['tools']
export function apply(ctx: Context, config: Config) {
  ctx.tools.register(defineTool({
    name: 'vault_search',
    description: '…',
    parameters: { query: { type: 'string', required: true } },
    async execute(args, exec) {
      // 观察(exec.signal)；返回规范 JSON 值
      return { hits: [...] }
    },
    output: {
      schema: { /* 规范值 schema */ },
      render: (_a, v) => [{ type: 'text', text: renderForModel(v) }],  // 模型可见内容
    },
    presentResult: (a, r) => ({ /* UI 卡片意图（可选，纯函数、重放安全） */ }),
  }))
}

参照：dsh-obsidian 的 8 个工具（plugins/dsh-obsidian/src/tools.ts）—— 注意每个工具自带安全边界（路径围栏、乐观锁、并发安全声明）。

④ HTTP API：自定前缀 + 自做信任检查

export const inject = ['webServer']
export function apply(ctx: Context, config: Config) {
  ctx.effect(() => {
    ctx.webServer.register({
      kind: 'prefix', path: '/my-plugin/api',
      handler(req, res) { /* GET 开放；POST 校验 Origin/sec-fetch-site */ },
    })
  }, 'my-plugin: http api')
}
  • 宿主没有全局鉴权中间件：每个路由的信任检查是插件自己的责任（参照 wecom 的 isTrustedMutationRequest、reading 的「有 Origin 必同源」、obsidian 的严格 mutationOrigin）；
  • 响应记得 Cache-Control: no-store / X-Content-Type-Options: nosniff；
  • API 永不外泄文件系统路径（参照 reading 的 PublicBook 模式）。

⑤ Web UI：声明 dsh.client，注册槽位

// package.json（节选）
{
  "exports": { ".": /* 宿主侧入口 */, "./client": "./lib/client.js" },
  "dsh": { "client": { "platform": "web", "inject": ["@deepseek-ai/dsh-client-runtime"] } }
}
// src/client/index.tsx —— 浏览器里的 cordis 插件
export const inject = ['slots']
export function apply(ctx: ClientContext): void {
  ctx.slots.inject('settings.plugins.tab', () =>
    ctx.slots.register(
      { name: 'settings.plugins.tab', id: 'my-plugin', order: 50, label: 'My Plugin' },
      SettingsPanel))
  ctx.effect(() => () => teardown(), 'my-plugin: client surfaces')
}
  • 宿主扫描 dsh.client → 暴露 /plugins/<pkg>/client.js?rev=<sha1> → __DSH_BOOT__ 注入 index.html —— 插件不需要碰前端构建；
  • 设置页 tab 想显示版本：import pkg from '../../package.json' with { type: 'json' } 构建期烘焙（参照 5543721 的做法）；
  • 浮层工作台范式：portal + 宿主 DOM 锚点 + 纯函数几何，不改宿主布局（参照 reading/obsidian 的 workbench-anchor）。

⑥ 打包成 bundle

my-plugin/
├── package.json       # dsh.bundle.patch + exports + prepare + peerDependencies
├── cordis.patch.yml   # insert 一行：id/name/inject/config（!!js 读环境）
├── lib/               # 构建产物：index.js + types + client.js（如含 UI）
└── src/
字段要求
"dsh".bundle.patch指向 cordis.patch.yml —— 有它才是 bundle，没有就是普通依赖（装了不激活）
main/types/exports产物必须覆盖所有声明的入口（含 ./client 与 bin）
preparegit 安装必需：pnpm 装完源码后运行它自举构建；必须自包含（不假设兄弟目录的 monorepo checkout）
peerDependencies锁宿主服务包版本（@deepseek-ai/cordis、dsh-agent、dsh-host-webserver…）—— 类型来自宿主随包发布的 .d.ts
version严格 SemVer；改了行为就 bump，永不复用已发布版本（我们 AGENTS.md 的纪律）
出树工程的类型技巧宿主对 Context 的声明合并在宿主编译单元内，插件工程看不到 —— 写一个本地 dsh-shims.d.ts 重建消费面的最小声明（参照 plugins/dsh-wecom/src/dsh-shims.d.ts）。这是官方 service.md「Declare its type」一节的实战形态。

⑦ 安装、更新与发布

  1. 试装：dsh plugin --profile web add ./my-plugin（本地路径）；
  2. 公开安装：push 到 GitHub 后 dsh plugin --profile web add 'github:you/repo#path:/plugins/my-plugin'；先在 profile 的 allowBuilds 里信任 git+https 与 git+ssh 两种归一化形态（pnpm 打印什么就复制什么）；建议 pin #<sha>；
  3. 验证树：dsh --profile web --dump-config 应能看到 # == my-plugin 层；
  4. 重启 profile（或等 live 层重放）→ 完成；
  5. 更新：monorepo 多插件仓库配一个 updater（--config.dlx-cache-max-age=0 dlx + GitHub Contents API 比对，参照 scripts/dsh-plugin-updater）；plain pnpm outdated 检测不到 Git 依赖的新 commit；
  6. 打 tag：插件 scoped tag（如 dsh-wecom-v0.5.2），先过 release:check。

发布前检查清单

维度检查项
行为可逆性：一切注册走 ctx / ctx.effect？卸载/HMR 后无残留（定时器 unref？连接关闭？）
配置两个部署可能不同的值都进了 Config schema？环境变量只在 patch 里读？默认值安全（空白名单=拒绝）？
依赖必需服务进 inject；可选服务 ctx.get 判空降级？目标 profile 缺服务时的行为可接受？
安全HTTP 变更接口有 Origin 检查？路径操作有围栏（realpath + symlink）？日志不含 secret/消息体？错误信息可诊断（错误码/错误栈分层）？
宿主演进对宿主内部结构的假设是否最小化并有版本探测（参照 wecom 的事件源探测链）？「摸宿主内部」的防护行为写进仓库纪律了吗？
打包prepare 自包含可构建？产物覆盖全部入口？peerDependencies 锁版本？version 已 bump 且未复用？repository.url/directory 正确？
重启安全插件的部署/重启操作绝不在 DSH 进程内的工具调用里执行（TOOL_OUTCOME_UNKNOWN 协议）？
最后一个视角写 dsh 插件的本质是：你写的不是「扩展某个应用的代码」，而是「给一棵插件树贡献一行配置 + 一个 Service 消费者」。你与官方 web-app、与模型适配器、与 agent 循环平起平坐 —— 这既是能力（你能做到官方插件做的一切），也是纪律（你要像官方作者一样对待可逆性、配置边界与安全默认）。
